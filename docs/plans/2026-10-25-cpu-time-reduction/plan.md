## 背景・目的

本番（Workers 無料プラン）の 1 リクエストあたり CPU 時間は中央値 96ms、範囲 20〜302ms で、無料プランの上限 10ms を大きく超えている。現時点で打ち切り（exceededCpu）は発生していないが、超過が続くと返信が届かなくなるおそれがある。

主因は構造的なものである。syumai/workers-go v0.36.0 はリクエストごとに Go の wasm インスタンスを新しく作って `main` を実行するため、`main` で行う処理がそのまま毎リクエストの CPU 時間になる。現在の `main` は `country.Default()` で go:embed した countries.json（約 86KB、196 件）を encoding/json で解析し、名前の索引（map）を組み立てている。ローカル計測（Node.js、同一の計測方法）では最小構成の Worker の起動が 5.5ms なのに対し本 bot は 15.6〜17.7ms で、差分の大半がこの解析と索引作成である。

この PR では、国データを JSON の実行時解析ではなく Go のコード（静的初期化されるテーブル）として持ち、起動時の処理をほぼゼロにする。あわせて、再現可能な CPU 時間の計測手順をリポジトリに入れ、ベースより明確に減ったことを数値で示す。10ms に収まることは保証しない（Go ランタイムの起動だけで 5.5ms＋αかかる）。

## 方針

### 1. データは Go の複合リテラルとして生成し、静的初期化に任せる

生成ファイル `internal/country/countries_gen.go` の形（概略）:

```go
// Code generated by tools/gencountrygo; DO NOT EDIT.

package country

const (
	generatedAt = "2026-10-24"
	source      = "Wikidata (https://www.wikidata.org/), CC0 1.0"
)

// countryTable is the data set in data/countries.json order.
var countryTable = [...]Country{
	{Code: "AD", NameJA: "アンドラ", AliasesJA: []string{"アンドラ公国"}, AliasesEN: []string{"Andorra"}, CapitalJA: "アンドラ・ラ・ベリャ", CapitalEN: "Andorra la Vella", Lat: 42.507222222, Lon: 1.522222222, WikipediaJAURL: "https://ja.wikipedia.org/wiki/%E3%82%A2%E3%83%B3%E3%83%89%E3%83%A9"},
	// ...
}

// countryIndex maps a normalized name or alias to an index into countryTable.
// It is sorted by Key and has no duplicates.
var countryIndex = [...]indexEntry{
	{Key: "andorra", Index: 0},
	// ...
}
```

- 文字列・数値・`[]string` だけで構成される配列の複合リテラルは Go コンパイラが静的初期化（データセグメントに配置）するため、実行時の初期化コードが走らない。map リテラルは実行時に挿入ループが走るので使わない
- 文字列は `strconv.Quote` 相当で出力する（日本語は印字可能文字なのでそのまま残り、差分が読める）。浮動小数は `strconv.FormatFloat(v, 'g', -1, 64)` で往復可能な最短表現にする。出力は `go/format` で整形する
- 索引エントリは `*Country` ではなく `countryTable` への添字（int）を持つ。コンパイラのポインタ静的化の可否に依存せず、確実に静的になる

### 2. countries.json は引き続きデータの正本。Go コードは派生物

- gencountries（Wikidata → countries.json）はそのまま。新ツール gencountrygo が countries.json → countries_gen.go を生成する。`internal/country/data.go` に `//go:generate go run ../../tools/gencountrygo -in data/countries.json -out countries_gen.go` を置く
- JSON を人が確認できる差分として残し、Wikidata に再問い合わせせずに Go コードだけ再生成できるようにするため、2 段構成にする
- 両者の同期はテストで保証する: `Load(countries.json)` の結果と `Default()` が、データ・索引・メタ情報のすべてで一致すること。崩れたときの失敗メッセージに再生成コマンドを含める
- countries.json は wasm に embed しない（本番ビルドに含まれるコード（`_test.go` 以外）から countries.json の `//go:embed` を削除）。テスト用 fixture の embed（`internal/country/country_test.go` の `testdata/fixture.json`）と、`tools/gencountries` の `query.sparql` の embed は対象外で残してよい。テストは `os.ReadFile("data/countries.json")` で読む

### 3. 索引はソート済みテーブル＋二分探索。Store の内部表現を統一する

- `Store` は `countries []*Country`（データ順）、`index []indexEntry`（キー昇順）、`generatedAt`、`source` を持つ。map は持たない
- 索引の構築規則は現状と同じ: 表示名（name_ja）の正規化キーが最優先、別名は表示名を上書きしない、複数の国で共有される別名は索引に入れない。この規則は `BuildIndex(countries []*Country) ([]IndexEntry, error)` として公開し、`Load`（JSON 経路。テストと生成ツールが使う）と生成ツールの両方が同じ実装を使う。キーの順序は `strings.Compare` によるバイト順で、重複は存在しない
- `Lookup` は `slices.BinarySearchFunc` で探す（196 件＋別名で約 10 回の比較）。`ByName(name)` は `Lookup(name)` の結果が `name` と完全一致する表示名を持つときだけ返す形にする。表示名の正規化キーは必ずその国を指し、別名に上書きされないため、既存の `byName` map と同じ結果になる（空白を含む入力など、正規化で一致しても表示名が異なる場合は nil）。この同値性はテストで固定する
- `Load(data []byte)` は残す（JSON 解析 → 検証 → `BuildIndex` → `newStore`）。検証は従来どおり `Load` で行い、生成ツールは `Load` が通ったデータだけをコード化する。実行時の `Default()` は検証を一切行わない
- `Default()` は `*Store` を返す（error を返さない）。`cmd/worker/main.go` の panic 分岐を削除する。`PickN`、`All`、`Len`、`GeneratedAt`、`Source`、`Country` のメソッド群の挙動は変えない

### 4. 起動時初期化の棚卸し

- `internal/` と `cmd/` を対象に、パッケージ変数の map リテラル、`init()`、`regexp.MustCompile`、重い `sync.Once` を列挙し、実装担当が実装報告に含め、采配役が PR 説明に載せる。変換は「静的テーブル化が機械的にでき、かつ挙動が変わらないもの」に限り、それ以外は記録に留める
- `flagsizes_gen.go` の `flagSizes` map（196 件）は、既定では変換しない（推定コストは 0.1ms 未満で、PR-A の生成ツールにも手が入るため）。計画承認時に「変更しない」と確定した

### 5. 計測方法

- `scripts/bench-cpu.mjs <path/to/app.wasm> [runs]`: wasm モジュールを 1 回だけコンパイルし、リクエストごとに `new Go()` と `WebAssembly.Instance` を作って `go.run` で起動する。`workers.ready` が呼ばれるまでを「起動」、`binding.handleRequest` の完了までを「処理」として `process.cpuUsage()`（user+system）を取る。既定 12 回実行し先頭 2 回を除いた中央値を出す。計測対象は `GET /`、署名付き webhook「日本」、同「クイズ」の 3 種
- Node の `fetch` 実装でボディ付き `Request` を作るには `duplex: "half"` が必要なので `globalThis.Request` を包む。workers-go の shim が参照する `globalThis.tryCatch` を定義する。返信 API は `http.createServer` のモックに向け、`LINE_API_BASE_URL` で差し替える。署名は `CHANNEL_SECRET` で HMAC-SHA256
- `wasm_exec.js` は `workers-assets-gen` が build/ に生成するものを使う。生成されない場合は Go ツールチェーン付属のもの（`$(go env GOROOT)/lib/wasm/wasm_exec.js`）を使い、スクリプト内で場所を解決する
- A/B は同じマシン・同じ Go ツールチェーンで、ベース SHA の wasm と変更後の wasm を交互に 3 回ずつ走らせ、中央値の中央値で比較する。Node の値は本番（workerd）より小さく出るため、絶対値ではなく相対比較とする
- 本番の確認は PR マージ後の手順とし、既存の計測と同じく wrangler tail の cpuTime を使う（完了条件を参照）

### 代替案を選ばなかった理由

- 静的 map リテラル: 実行時に挿入ループが走るため、ゼロにはならない。数百件なら 1ms 未満と見込まれるが、二分探索で済むなら持たない方が単純
- 初回 Lookup 時に索引を遅延構築: webhook のほぼ全経路で Lookup または ByName が呼ばれるため、実質的な削減にならない
- gencountries から直接 Go を出力して JSON を廃止: Wikidata への再問い合わせなしに再生成できなくなり、データ差分のレビュー性も下がる

## 公開経路

1. 実装担当が作業ブランチ plan/2026-10-25-cpu-time-reduction に、計画書（plan.md / request.md）と実装を commit する（push はしない）
2. 検収後、采配役が push し、main へ向けた単独の PR を作成する。実装担当が実装報告に含めた計測結果表・棚卸し結果・プロファイル上位を、采配役が PR 説明に載せる
3. CI（test job）が緑であることを確認し、利用者が許可すればマージする
4. 本番デプロイ（`wrangler deploy`）は利用者の承認を得てから行う。デプロイ後に wrangler tail で事後確認を行い、結果を利用者に報告する。悪化や exceededCpu が見られた場合はベース SHA の状態に戻す
