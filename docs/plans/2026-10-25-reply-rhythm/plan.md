## 背景・目的

現在の bot は Webhook を受け取るとすぐに返信 API を呼ぶため、2〜3 通の返答が一瞬で並んで届き、会話としての間がない。利用者は「考えてから答える」ようなリズムを望んでいる。

この変更後は、利用者がメッセージを送る（またはクイズの選択肢を押す）と、トーク画面にローディングのアニメーション（入力中の「…」）が表示され、1 秒ほど置いてから従来どおりの返答がまとめて届く。返答の文言・順序・通数は変えない。プッシュ送信は使わないため、無料の通数枠は消費しない。

## スコープ

- 対象:
  - `internal/line/client.go`: ローディング表示 API（`POST /v2/bot/chat/loading/start`）を呼ぶメソッドの追加と、返信 API と共通の送信・エラー処理の整理
  - `internal/app/handler.go`: 返答がある 1 対 1 のイベントで「ローディング表示 → 待機 → 返信」の順に処理する。待機は Webhook への 200 応答を返す前にハンドラ内で行う
  - `internal/app/config.go`（既存の設定読み込み）: 待機時間を環境変数で調整できるようにする（既定値あり、未設定でも動く）
  - `internal/app` の `Deps`: 待機処理を差し替え可能にする（テストで実時間を待たないため）
  - ログ: ローディング表示の成否をステータスと分類だけで出す
  - `scripts/local-smoke.mjs`: モックがローディング API 呼び出しを受け取ることと、呼び出し順序・経過時間の確認を追加
  - 上記のテスト（`internal/line`、`internal/app`）
  - README 等に環境変数の一覧がある場合はその更新
- 対象外:
  - 返答メッセージの文言・構成・通数の変更
  - 1 通ずつ時間差で送る方式、プッシュ送信
  - 200 応答後に処理を続ける方式（`WaitUntil`）の採用
  - グループトーク・複数人トークでのローディング表示（API が 400 を返すため対象外。従来どおり即時に返信する）
  - workers-go のバージョン更新

## 方針

**処理順序（イベントごと）**

1. 従来どおり `bot.Respond` で返答を決める。
2. 返答メッセージがあり、応答トークンがあり、送信元が 1 対 1（`source.type == "user"` かつ `userId` あり）の場合だけ、ローディング表示 API を `chatId = userId`、`loadingSeconds = 5`（指定できる最小値）で呼ぶ。
3. 待機する。待機は `Deps` から注入した関数で行い、既定実装はタイマーと `ctx.Done()` の両方を待つ（リクエストの context が終われば待機をやめる）。
4. 返信 API を呼ぶ。返信が届いた時点でローディングは自動的に消える。
5. すべてのイベントを処理してから 200 を返す。

**契約・不変条件**

- LINE は bot サーバーが Webhook に 2 秒以内に応答を返さない場合を `request_timeout` のエラーとして扱う（[Webhook のエラー統計の確認方法](https://developers.line.biz/ja/docs/messaging-api/check-webhook-error-statistics/)）。待機は 200 応答の前に行うため、待機時間＋ローディング API と返信 API の通信＋処理時間が 2 秒未満に収まる必要がある。このため待機時間の上限を 1200ms とし、それを超える設定値は上限に丸めて設定警告を出す。応答トークンの利用期限（Webhook 受信から 1 分以内）もこの上限で十分に守られる。
- ローディング表示 API の失敗は返信を止めない。失敗時はステータスと分類だけをログに出し、返信は従来どおり行う。失敗時は待機せずにすぐ返信する（計画承認時に確定）。
- 待機時間が 0 のときはローディング表示も待機も行わず、現在の挙動と完全に一致する（緊急時の切り戻しに使える）。
- 待機は Webhook への応答を返す前に行う。workers-go v0.36.0 ではハンドラが応答を返した後の処理が不安定なため、`WaitUntil` は使わない。
- ログに利用者 ID・発言・トークンを含めない（既存の不変条件を維持）。ローディングの結果は `loading=ok|skipped|failed` のような固定語で出す。
- `line.Client` のエラー型は返信・ローディングで共通にする。`APIError` と `ErrSend` のメッセージ文言が「reply」固定なら、どの API かが分かる形に一般化する。既存テストが文言ではなく `errors.Is` / `errors.As` で判定していることを確認し、文言一致のテストがあれば合わせて直す。

**設定**

- 環境変数 `REPLY_DELAY_MS`（整数ミリ秒）。未設定・空なら既定値 1000（計画承認時に確定）。不正な値は既定値にして設定警告を出す。上限 1200（超える値は上限に丸めて設定警告）。
- wrangler の設定ファイルには追加しない（既定値で動くため）。ローカル確認用に `.dev.vars` の例があれば追記する。

**Workers 実行環境**

- Go の wasm ランタイムではタイマー待機は JS のタイムアウトに委ねられ、CPU 時間を消費しない。ハンドラがまだ応答を返していない間なので、workers-go の FAQ にある不安定ケースには当たらない。
- fetch が 1 回増えるが、fetch 待ちも CPU 時間に含まれない。
- この前提は机上のもののため、`node scripts/local-smoke.mjs`（wrangler dev 上）で「ローディング → 待機 → 返信」の順と経過時間を実測することを完了条件に含める。

**選ばなかった案**

- 200 を返してから `WaitUntil` で待機・返信する案: workers-go v0.36.0 で不安定と明記されているため不採用。
- 1 通ずつ時間差で送る案: 応答トークンが 1 回しか使えずプッシュ送信が必要になるため不採用（利用者も不採用を選択済み）。

## 未確定事項・リスクと判断の委ね方

計画承認時に確定した事項:

- 待機時間: 既定 1000ms。環境変数 `REPLY_DELAY_MS` で変更でき（上限 1200ms で、超える値は上限に丸めて設定警告。0 でローディング表示も待機もしない＝現在の挙動）、不正値は既定値にして設定警告を出す。Webhook には 2 秒以内に応答する必要があり、通信・処理時間の余裕を残すためこの値とする
- ローディング表示に失敗したとき: 待たずにすぐ返信する
- 1 回の Webhook に複数イベントがあるとき: 待機は最初に返信するイベントの前の 1 回だけ。ローディング表示は該当イベントごとに行う

| 項目 | 内容 | 実装時の扱い |
|---|---|---|
| LINE の Webhook タイムアウト | bot サーバーが 2 秒以内に応答しないと `request_timeout` のエラーになる。待機は 200 応答の前に行うため、待機時間＋ローディング API と返信 API の通信＋処理時間が 2 秒未満に収まる必要がある | 既定 1000ms・上限 1200ms で通信・処理時間の余裕を取る。`wrangler dev` 上の smoke で Webhook 送信から 200 受信までの経過時間を実測し、2000ms 未満であることを確認する。デプロイ後は LINE Developers コンソールの Webhook エラー統計で `request_timeout` が出ていないことを利用者が確認する。設計上の変更は止まって報告 |
| Go wasm での待機が Workers 上で動くか | 机上では問題ないが未実測 | wrangler dev 上の `node scripts/local-smoke.mjs` で実測する。待機が効かない・ハンドラが途中で終わる場合は止まって報告し、`WaitUntil` には切り替えない |
| CPU 時間 | fetch が 1 回増えるが待機は CPU 時間に含まれない。JSON 生成分が数ms増える可能性 | smoke と既存の計測手段で大きな増加がないことを確認。本番値の確認はデプロイ後に委ねる |
| エラー文言の一般化 | `APIError` / `ErrSend` の文言変更が既存テストに影響する可能性 | 文言一致のテストがあれば合わせて直してよい。公開 API のシグネチャ変更は止まって報告 |
| ローディングが表示されない条件 | トーク画面を開いていない・未友だち・ブロック中は 202 でも表示されない | API 仕様どおりで対処不要。利用者には実機確認時の前提として伝える |
